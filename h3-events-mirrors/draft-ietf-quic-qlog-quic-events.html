1. Introduction

This document defines a qlog event schema (Section 8 of [QLOG-MAIN]) containing concrete events for the core QUIC protocol (see [QUIC-TRANSPORT], [QUIC-RECOVERY], and [QUIC-TLS]) and some of its extensions (see [QUIC-DATAGRAM], [GREASEBIT], and [RESET-STREAM-AT]).¶

The event namespace with identifier quic is defined; see Section 2. In this namespace multiple events derive from the qlog abstract Event class (Section 7 of [QLOG-MAIN]), each extending the "data" field and defining their "name" field values and semantics. The data types that the events use are defined in Section 8.¶

1.1. Use of group IDs

QUIC's Original Destination Connection ID (ODCID) can be used as the value of the qlog group_id field. The ODCID is the connection ID that the client chooses for its first Initial packet. It stays the same for the whole connection, unlike the connection IDs that endpoints use, which can change. It can also link packets such as Retry and Version Negotiation to the connection.¶

The ODCID can also be used as the qlog filename or file identifier, optionally suffixed by the vantage point type. For example, abcd1234_server.qlog would contain the server-side trace of the connection with ODCID abcd1234.¶

1.2. Raw packet and frame information

Protected QUIC packets (Initial, 0-RTT, Handshake, and 1-RTT) end with an AEAD authentication tag. Every cipher suite that QUIC version 1 can use has a 16-byte tag; see Section 5.3 of [QUIC-TLS]. When calculating the lengths in RawInfo fields (Section 10 of [QLOG-MAIN]) for these packets, the tag is treated as a 16-byte trailer.¶

1.3. Events without a known connection

A qlog trace is typically associated with a single QUIC connection. However, some events cannot be tied to a specific connection, especially on the server. For example, a packet_dropped event (Section 5.7) with the trigger connection_unknown is for a packet that matches no known connection.¶

There are various ways to handle these events, each with tradeoffs between file size overhead, flexibility, ease of use, and ease of implementation. Some options include:¶

  • Log them in a separate endpoint-wide trace, or use a special group_id value, not associated with a single connection.¶

  • Log them in the most recently used trace.¶

  • Use additional heuristics to identify the connection, for example the four-tuple in addition to the connection ID.¶

  • Buffer events until they can be assigned to a connection, for example events about the Version Negotiation and Retry packets that a server sends before it creates connection state.¶

1.4. Notational Conventions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

The event and data structure definitions in this document are expressed in the Concise Data Definition Language [CDDL] and its extensions described in Section 1.2 of [QLOG-MAIN].¶

This document uses the following from [QLOG-MAIN]: the event namespace and event type concepts; the name, data, tuple, group_id, and time-related fields; and the RawInfo type.¶

Events are defined with an importance level as described in Section 8.3 of [QLOG-MAIN].¶

As is the case for [QLOG-MAIN], the qlog schema definitions in this document are intentionally agnostic to serialization formats. The choice of format is an implementation decision.¶

2. Event Schema Definition

This document describes how the core QUIC protocol and selected extensions can be expressed in qlog using a newly defined event schema. Per the requirements in Section 8 of [QLOG-MAIN], this document registers the quic namespace. The event schema URI is urn:ietf:params:qlog:events:quic.¶

2.1. Draft Event Schema Identification

This section is to be removed before publishing as an RFC.¶

Only implementations of the final, published RFC can use the events belonging to the event schema with the URI urn:ietf:params:qlog:events:quic. Until such an RFC exists, implementations MUST NOT identify themselves using this URI.¶

Implementations of draft versions of the event schema MUST append the string "-" and the corresponding draft number to the URI. For example, draft 07 of this document is identified using the URI urn:ietf:params:qlog:events:quic-07.¶

The namespace identifier itself is not affected by this requirement.¶

4. Connectivity events

4.1. server_listening

The server_listening event is emitted when the server starts accepting connections. It has Extra importance level.¶

Some QUIC stacks do not handle sockets directly, so they cannot log IP addresses or ports.¶

4.2. connection_started

The connection_started event is emitted when a client attempts a new connection, or when a server accepts one. It overlaps with the connection_state_updated event, but it also logs the local and remote endpoint information. It has Base importance level.¶

Some QUIC stacks do not handle sockets directly, so they cannot log IP addresses or ports. All fields of TupleEndpointInfo (Figure 44) are optional, so such a stack can log local and remote with only the fields it knows, such as connection_ids.¶

4.3. connection_closed

The connection_closed event is emitted when a connection closes, typically because of an error or a timeout. It has Base importance level.¶

This event overlaps with the connection_state_updated event and the CONNECTION_CLOSE frame. However, when analyzing large deployments, it can be useful to have a single event for each closure, with a reason field for more detail. This event can also log closures due to timeouts or explicit application actions, such as racing several connections and aborting the slowest, which the other events cannot easily capture.¶

The connection_closed event is logged when the local endpoint does one of the following; see Section 10 of [QUIC-TRANSPORT]:¶

  • silently discards the connection after an idle timeout;¶

  • sends a CONNECTION_CLOSE frame, and enters the closing state;¶

  • receives a CONNECTION_CLOSE frame, and enters the draining state; or¶

  • receives a Stateless Reset, and enters the draining state.¶

Later changes, such as leaving the closing or draining state, are logged with the connection_state_updated event.¶

QUIC has two kinds of connection error, transport errors and application errors, each with defined codes and semantics; see Section 20 of [QUIC-TRANSPORT]. An implementation can also have internal errors, which it might or might not map to these codes. So this event can carry two levels of error: connection_error or application_error for the QUIC error, and internal_code for a more specific internal error.¶

If the error code does not map to a known error string, the connection_error or application_error value of "unknown" type can be used and the raw value captured in the error_code field; a numerical value without variable-length integer encoding.¶

Implementations SHOULD use the most descriptive trigger value that they can determine. This is often clear at the endpoint that closes the connection, but can be less clear at the endpoint that receives the CONNECTION_CLOSE frame.¶

4.4. connection_id_updated

The connection_id_updated event is emitted when either endpoint updates its current connection ID. This typically happens rarely during a connection, so logging this event is more efficient than logging the connection ID in every packet_sent or packet_received event. It has Base importance level.¶

The connection_id_updated event is viewed from the perspective of the endpoint applying the new ID. When the endpoint receives a new connection ID from the peer, the initiator field is "remote". When the endpoint updates its own connection ID, the initiator field is "local".¶

4.5. spin_bit_updated

The spin_bit_updated event is emitted when the value of the QUIC latency spin bit changes; see Section 17.4 of [QUIC-TRANSPORT]. It SHOULD NOT be emitted when the spin bit is set to the value it already has. It has Base importance level.¶

4.6. connection_state_updated

The connection_state_updated event is emitted when the connection changes state, to track progress through the QUIC handshake and connection close. It has Base importance level.¶

[QUIC-TRANSPORT] does not define a complete set of connection states or their transitions, though it names some, such as the closing and draining states. This document defines the states most likely to be useful for debugging QUIC connections; the list is not exhaustive.¶

QUIC implementations SHOULD log the BaseConnectionStates, and can add the GranularConnectionStates when more in-depth debugging is required. Tools SHOULD handle both kinds equally.¶

The connection_state_updated event overlaps with the connection_closed and connection_started events, and with the frames logged in events such as packet_received. Still, it can be useful to log state transitions separately, especially if they map to an internal state machine. Implementations can therefore use other ConnectionState values that match their internal logic. Tools SHOULD handle these custom states in a similar way to the states defined in this document.¶

4.7. tuple_assigned

The tuple_assigned event associates a TupleID with the details of a network tuple, such as its IP addresses, ports, and connection IDs. It has Base importance level.¶

As described in Section 7.2 of [QLOG-MAIN], each qlog event can be linked to a single network tuple by its top-level tuple field, whose value is a TupleID. Encoding tuple details, such as IP addresses or connection IDs, into the TupleID itself can be cumbersome. This event records them separately, so TupleIDs can stay short, and their details can be updated as the connection evolves.¶

Implementations choose their own tuple_id values. For example, a TupleID can be an incrementing integer, the first Destination Connection ID associated with the tuple (or its sequence number), or the two endpoint IP addresses or a hash of them.¶

The empty string ("") is a valid TupleID, and it is the default for events that do not set the tuple field. So the initial tuple of a QUIC connection, on which the handshake occurs (see Section 4.2), is implicitly associated with the TupleID "". Details for this default tuple can be logged with a tuple_assigned event whose tuple_id is "".¶

Because a tuple's details can change during the connection, a TupleID can appear in several tuple_assigned events, and the latest one holds its current details. The first tuple_assigned event for a TupleID indicates that the TupleID was created, and later ones indicate updates. An event with both tuple_local and tuple_remote omitted indicates that the TupleID was abandoned.¶

4.8. mtu_updated

The mtu_updated event indicates that the estimated Path MTU was updated. This happens as part of Path MTU discovery; see Section 14 of [QUIC-TRANSPORT]. It has Extra importance level.¶

5. Transport events

5.1. version_information

The version_information event supports QUIC version negotiation; see Section 6 of [QUIC-TRANSPORT]. It has Core importance level.¶

QUIC endpoints each have their own list of QUIC versions they support. The client uses the most likely version in their first initial. If the server does not support that version, it replies with a Version Negotiation packet, which contains its supported versions. From this, the client selects a version. The version_information event aggregates all this information in a single event type. It also allows logging of supported versions at an endpoint without actual version negotiation needing to happen.¶

Intended use:¶

  • When sending an initial, the client logs this event with client_versions and chosen_version set¶

  • Upon receiving a client initial with a supported version, the server logs this event with server_versions and chosen_version set¶

  • Upon receiving a client initial with an unsupported version, the server logs this event with server_versions set and client_versions to the single-element array containing the client's attempted version. The absence of chosen_version implies no overlap was found¶

  • Upon receiving a version negotiation packet from the server, the client logs this event with client_versions set and server_versions to the versions in the version negotiation packet and chosen_version to the version it will use for the next initial packet. If the client receives a set of server_versions with no viable overlap with its own supported versions, this event should be logged without the chosen_version set¶

5.2. alpn_information

The alpn_information event supports Application-Layer Protocol Negotiation (ALPN) over the QUIC transport; see [RFC7301] and Section 8.1 of [QUIC-TLS]. It has Core importance level.¶

QUIC endpoints are configured with a list of supported ALPN identifiers. Clients send the list in a TLS ClientHello, and servers match against their list. On success, a single ALPN identifier is chosen and sent back in a TLS ServerHello. If no match is found, the connection is closed.¶

ALPN identifiers are byte sequences that may be presentable as UTF-8. The ALPNIdentifier type supports either format. Implementations SHOULD log at least one format, but MAY log both or none.¶

Intended use:¶

  • When sending an initial, the client logs this event with client_alpns set¶

  • When receiving an initial with a supported alpn, the server logs this event with server_alpns set, client_alpns equalling the client-provided list, and chosen_alpn to the value it will send back to the client.¶

  • When receiving an initial with an alpn, the client logs this event with chosen_alpn to the received value.¶

  • Alternatively, a client can choose to not log the first event, but wait for the receipt of the server initial to log this event with both client_alpns and chosen_alpn set.¶

5.3. parameters_set

The parameters_set event groups settings from several sources, such as transport parameters and the TLS cipher suite, into a single event. This keeps the number of events low, and lets a reader reason about what the settings do without needing to know which mechanism set each one. It has Core importance level.¶

Most of these settings are set once and never change. However, they are often set at different times during the connection, so a trace can contain several parameters_set events with different fields set.¶

Some settings have two values: one set by the local endpoint, and one requested by the peer. The initiator field says which side the settings in an event come from, so it MUST be correct for every setting in that event. Local and remote settings MUST be logged in separate events. If the local endpoint changes its behavior based on the peer's settings, the outcome can be logged with a new event type, or with fields added through $$quic-parametersset-extension; see Section 8.2 of [QLOG-MAIN].¶

Each setting starts the connection with its default value, or with no value if it has no default. A parameters_set event that includes a setting replaces its previous value; settings that the event omits keep their values.¶

Implementations are not required to recognize, process, or support every parameter that they receive. For example, QUIC implementations ignore transport parameters that they do not support; see Section 7.4.2 of [QUIC-TRANSPORT]. The unknown_parameters field can log the raw values of such parameters, for example reserved (GREASE) parameters, private extensions, or experiments.¶

In the case of connection resumption and 0-RTT, some of the server's parameters are stored up-front at the client and used for the initial connection startup. They are later updated with the server's reply. In these cases, utilize the separate parameters_restored event to indicate the initial values, and this event to indicate the updated values, as normal.¶

5.4. parameters_restored

When using QUIC 0-RTT, clients are expected to remember and restore the server's transport parameters from the previous connection. The parameters_restored event is used to indicate which parameters were restored and to which values when utilizing 0-RTT. It has Base importance level.¶

Note that not all transport parameters should be restored (many are even prohibited from being re-utilized). The ones listed here are the ones expected to be useful for correct 0-RTT usage.¶

5.5. packet_sent

The packet_sent event indicates that a QUIC packet was sent. It has Core importance level.¶

The encryption level and packet number space are not logged explicitly, because header.packet_type implies them for the packet types that have them.¶

The datagram_payload_checksum field is described in Section 9.¶

5.6. packet_received

The packet_received event indicates that a QUIC packet was received. It has Core importance level.¶

The encryption level and packet number space are not logged explicitly, because header.packet_type implies them for the packet types that have them.¶

The datagram_payload_checksum field is described in Section 9.¶

5.7. packet_dropped

The packet_dropped event indicates that a QUIC packet was dropped. It has Base importance level.¶

The trigger field gives a general reason for dropping the packet, and the details field can hold additional implementation-specific information. Some example situations for each trigger value include:¶

  • internal_error: not initialized, out of memory¶

  • rejected: limits reached, DDoS protection, unwilling to track more paths¶

  • unsupported: unknown or unsupported version¶

  • invalid: packet parsing or validation error¶

  • duplicate: duplicate packet¶

  • connection_unknown: packet does not relate to a known connection or connection ID¶

  • decryption_failure: decryption failed¶

  • key_unavailable: decryption key was unavailable¶

  • general: situations not clearly covered in the other categories¶

Packets dropped as unsupported or connection_unknown often cannot be tied to a connection; see Section 1.3.¶

The datagram_payload_checksum field is described in Section 9.¶

5.8. packet_buffered

The packet_buffered event is emitted when a packet is buffered because it cannot be processed yet, for example because the keys to decrypt it are not yet available. Its full contents can be logged later, in a packet_received event, once it is processed. It has Base importance level.¶

The datagram_payload_checksum field is described in Section 9.¶

5.9. packets_acked

The packets_acked event is emitted when one or more sent packets are acknowledged by the peer for the first time. It has Extra importance level.¶

Successive ACK frames can acknowledge the same packet, but this event is emitted only for the first acknowledgment of each packet. This information can also be deduced from received ACK frames, though finding the first acknowledgment needs extra processing. Implementations that do not log frame contents can use this event instead.¶

If packet_number_space is omitted, its value is application_data, the packet number space that most packets in a typical QUIC connection use.¶

5.10. udp_datagrams_sent

The udp_datagrams_sent event indicates that one or more UDP datagrams were passed to the network socket. It can show how QUIC packet buffers are drained to the operating system. It has Extra importance level.¶

The RawInfo fields exclude UDP headers, because QUIC implementations do not always handle UDP directly.¶

The datagram_payload_checksums field is described in Section 9.¶

5.11. udp_datagrams_received

The udp_datagrams_received event indicates that one or more UDP datagrams were received from the network socket. It can show how the operating system passes datagrams to the user-space stack. It has Extra importance level.¶

The datagram_payload_checksums field is described in Section 9.¶

5.12. udp_datagram_dropped

The udp_datagram_dropped event indicates that a UDP datagram was dropped, typically because it does not contain a valid QUIC packet. If the datagram contains a valid QUIC packet that is dropped for another reason, the packet_dropped event (Section 5.7) is used instead. It has Extra importance level.¶

5.13. stream_state_updated

The stream_state_updated event is emitted when the state of a QUIC stream changes; see Section 3 of [QUIC-TRANSPORT]. Most state changes can be inferred from the frames that are sent and received, but an explicit event can be easier to use. It has Base importance level.¶

QUIC stream IDs encode whether a stream is unidirectional or bidirectional (see Section 2.1 of [QUIC-TRANSPORT]), but the optional stream_type field states it directly.¶

Section 3 of [QUIC-TRANSPORT] describes the sending and receiving parts of a stream, each with its own state machine. The stream_side field says which part's state changed. If both parts change state at the same time, for example when both become closed, two events with different stream_side values SHOULD be logged.¶

QUIC implementations SHOULD log the BaseStreamStates, and can add the GranularStreamStates when more in-depth debugging is required. Tools SHOULD handle both kinds equally.¶

The trigger field can show which endpoint initiated a state change, for example when a stream is closed because of a RESET_STREAM or STOP_SENDING frame.¶

5.14. Frame-related events

While the packet_sent (Section 5.5) and packet_received (Section 5.6) events can convey all frames contained in a single QUIC packet, some implementations might not be able or willing to include frame information at the moment either event is logged.¶

The frames_created and frames_parsed events log frames independently of packets.¶

A qlog trace can contain both packet- and frame-related events. However, it is RECOMMENDED that implementations avoid generating events with duplicate or redundant frame information, since doing so inflates the size of logs.¶

Where an implementation logs both packet- and frame-related events, the optional packet_numbers field in frame-related events can be used to link frames to packets explicitly. The field is an array so that a single event can log frames that belong to different packets. The frames and packet_numbers arrays are mapped to each other by the position and order of their entries. If the packet_numbers field is logged, every frame MUST have a corresponding packet number at the same index.¶

For example, an instance of the frames_parsed event that represents four STREAM frames received over two packets can be serialized as:¶

"frames":[
  {"frame_type":"stream","stream_id":0,"offset":0,"raw":{"length":5}},
  {"frame_type":"stream","stream_id":0,"offset":5,"raw":{"length":5}},
  {"frame_type":"stream","stream_id":1,"offset":0,"raw":{"length":9}},
  {"frame_type":"stream","stream_id":1,"offset":9,"raw":{"length":9}}
],
"packet_numbers":[
  1,
  1,
  2,
  2
]
¶

Frame-related events omit information that is available in the packet_received or packet_sent event, such as the packet's encryption level. Use cases that need such information are better served by those events.¶

Extensions can use frame-related events to log information that is not available when a packet event is logged, for example because frame processing was deferred.¶

5.14.1. frames_created

The frames_created event indicates that a set of QUIC frames was created. It has Extra importance level.¶

5.14.2. frames_parsed

The frames_parsed event indicates that a set of QUIC frames was parsed. It has Extra importance level.¶

5.15. stream_data_moved

The stream_data_moved event indicates that QUIC stream data moved between layers. It has Base importance level.¶

For example, data can move from an application protocol such as HTTP/3 to QUIC stream buffers, or the other way. Logging these moves can show the flow of data, how long data stays in each buffer, and the overhead introduced by each layer.¶

This event can also show whether received stream data is passed to the application protocol immediately or in batches. Data can be passed, for example, once per received packet, or in a batch after all received packets are processed. This can help identify bottlenecks, flow control issues, or scheduling problems.¶

The raw.length field gives the number of bytes moved. Because this event covers stream data only, there are no packet or frame headers, and raw.length MUST reflect that.¶

The additional_info field can log information about the stream state. For example, an application that moves data into the transport and ends the stream at the same time can log fin_set. A transport that has received an instruction to reset a stream can tell the application with stream_reset. In both cases, raw.length can be omitted or be zero.¶

This event covers only data in QUIC streams. For data in QUIC datagrams, see the datagram_data_moved event (Section 5.16).¶

5.16. datagram_data_moved

The datagram_data_moved event indicates that QUIC datagram data (see [QUIC-DATAGRAM]) moved between layers. It has Base importance level.¶

For example, data can move from an application protocol such as WebTransport to QUIC buffers, or the other way. Logging these moves can show the flow of data, how long data stays in each buffer, and the overhead introduced by each layer.¶

This event can also show whether received datagram data is passed to the application protocol immediately or in batches. Data can be passed, for example, once per received packet, or in a batch after all received packets are processed. This can help identify bottlenecks or scheduling problems.¶

The raw.length field gives the number of bytes moved. Because this event covers datagram data only, there are no packet or frame headers, and raw.length MUST reflect that.¶

This event covers only data in QUIC datagrams. For data in QUIC streams, see the stream_data_moved event (Section 5.15).¶

5.17. connection_data_blocked_updated

The connection_data_blocked_updated event indicates that the QUIC connection became blocked or unblocked for sending data. It has Extra importance level.¶

Depending on the reason, a blocked connection cannot send stream data, datagram data, or both, until that reason is resolved. The stream_data_blocked_updated and datagram_data_blocked_updated events give more detail for each type of data.¶

5.18. stream_data_blocked_updated

The stream_data_blocked_updated event indicates that a QUIC stream became blocked or unblocked for sending. It has Extra importance level.¶

5.19. datagram_data_blocked_updated

The datagram_data_blocked_updated event indicates that QUIC datagrams became blocked or unblocked for sending. It has Extra importance level.¶

5.20. migration_state_updated

The migration_state_updated event logs the progress of a connection migration by a client; see Section 9 of [QUIC-TRANSPORT]. It has Extra importance level.¶

Most details of a migration can be inferred from PATH_CHALLENGE and PATH_RESPONSE frames, together with tuple_assigned events. However, it can be useful to log the progress of the migration, and any decisions made, in a single event.¶

The MigrationState values follow the steps in Section 9 of [QUIC-TRANSPORT]: the probing_* values cover probing a new path (Section 9.1 of [QUIC-TRANSPORT]), and the migration_* values cover migrating the connection (Section 9.2 of [QUIC-TRANSPORT]).¶

Implementations that log per-path information in migration_state_updated events SHOULD also emit tuple_assigned events, to serve as the ground truth for tuple information.¶

5.21. timer_updated

The timer_updated event is emitted when a timer changes state. It has Extra importance level.¶

The event_type field takes one of three values:¶

  • set: the timer is set, and delta gives the time until it triggers¶

  • expired: the timer expired¶

  • cancelled: the timer was cancelled¶

An update to an active timer's timeout is logged as a new set event.¶

The recovery timer types correspond to timers in Section 6 of [QUIC-RECOVERY] and Appendix A.8 of [QUIC-RECOVERY]:¶

  • ack: the time threshold loss detection timeout¶

  • pto: the probe timeout¶

  • loss_timeout: the single, multi-modal loss detection timer that covers both¶

QUIC uses a variety of timers, and how they are used can depend on the implementation. Implementers can add fields to this event through $$quic-timerupdated-extension, or add timer types through $TimerType.¶

6. Security Events

6.1. key_updated

The key_updated event indicates that a key was installed or updated. It has Base importance level.¶

This happens when TLS provides new keys during the handshake, and at each 1-RTT key update; see Section 6 of [QUIC-TLS].¶

The key_phase field holds the full key phase, which identifies the generation of keys; it corresponds to @M and @N in Figure 9 of Section 6 of [QUIC-TLS]. The Key Phase bit in the packet header is the least significant bit of this value.¶

6.2. key_discarded

The key_discarded event indicates that a key was discarded. It has Base importance level.¶

Keys are discarded, for example, when the connection moves to a new encryption level during the handshake, or after a key update; see Section 4.9 of [QUIC-TLS].¶

7. Recovery events

Most of the events in this section are kept generic to support different recovery approaches and congestion control algorithms. The old, new, and trigger fields of congestion_state_updated, for instance, are free text, so their values depend on the algorithm.¶

Tools that process these events SHOULD try to handle such values even when they don't recognize them. For example, a tool that plots congestion states on a timeline can label an unknown state with the value of the new field.¶

7.1. recovery_parameters_set

The recovery_parameters_set event groups initial parameters from both loss detection and congestion control into a single event. It has Base importance level.¶

These parameters are typically set once and never change. Implementations that change them during the connection MAY emit the recovery_parameters_set event more than once.¶

The reordering_threshold field contains the packet threshold for loss detection, or "disabled" if packet-threshold loss detection is disabled.¶

Parameters that this document does not define, such as those of other loss detection and recovery algorithms, can be added through $$quic-recoveryparametersset-extension.¶

7.2. recovery_metrics_updated

The recovery_metrics_updated event is emitted when one or more of the observable recovery metrics change value. It has Core importance level.¶

Implementations SHOULD group all metric updates that happen at or around the same time into a single recovery_metrics_updated event. For example, if min_rtt and smoothed_rtt change at the same time, they are logged in one event, not two. Each event is only guaranteed to contain at least one of the listed metrics.¶

To make logging easier, implementations MAY log values that are the same as previously reported values; for example, two consecutive recovery_metrics_updated events can report the same min_rtt. However, implementations SHOULD try to log only values that changed.¶

Metrics that this document does not define, such as those of other loss detection and recovery algorithms, can be added through $$quic-recoverymetricsupdated-extension.¶

7.3. congestion_state_updated

The congestion_state_updated event indicates when the congestion controller enters a significant new state and changes its behaviour. It has Base importance level.¶

The values of the event's fields are intentionally unspecified here in order to support different Congestion Control algorithms, as these typically have different states and even different implementations of these states across stacks. For example, for the algorithm defined in the QUIC Recovery RFC ("enhanced" New Reno), the following states are used: Slow Start, Congestion Avoidance, Application Limited and Recovery. Similarly, states can be triggered by a variety of events, including detection of Persistent Congestion or receipt of ECN markings.¶

The trigger field SHOULD be logged if there are multiple ways in which a state change can occur but MAY be omitted if a given state can only be due to a single event occurring (for example Slow Start is often exited only when ssthresh is exceeded).¶

7.4. packet_lost

The packet_lost event is emitted when a packet is deemed lost by loss detection. It has Core importance level.¶

It is RECOMMENDED to populate the optional trigger field in order to help disambiguate among the various possible causes of a loss declaration.¶

7.5. marked_for_retransmit

The marked_for_retransmit event indicates which data was marked for retransmission upon detection of packet loss (see packet_lost). It has Extra importance level.¶

Similar to the reasoning for the frames_sent and frames_parsed events, in order to keep the amount of different events low, this signal is grouped into in a single event based on existing QUIC frame definitions for all types of retransmittable data.¶

Implementations retransmitting full packets or frames directly can just log the constituent frames of the lost packet here (or do away with this event and use the contents of the packet_lost event instead). Conversely, implementations that have more complex logic (e.g., marking ranges in a stream's data buffer as in-flight), or that do not track sent frames in full (e.g., only stream offset + length), can translate their internal behaviour into the appropriate frame instance here even if that frame was never or will never be put on the wire.¶

Much of this data can be inferred if implementations log packet_sent events (e.g., looking at overlapping stream data offsets and length, one can determine when data was retransmitted).¶

7.6. ecn_state_updated

The ecn_state_updated event indicates a progression in the ECN state machine as described in Appendix A.4 of [QUIC-TRANSPORT]. It has Extra importance level.¶

8.5. TupleEndpointInfo

TupleEndpointInfo describes one half, or direction, of a four-tuple. A full tuple has two halves: the server sends to the client's IP address and port, and the client sends to the server's IP address and port. Each direction uses its own destination connection ID.¶

Structures that log tuple information SHOULD therefore include two TupleEndpointInfo instances, one for each half of the tuple.¶

8.8. PacketHeader

If the packet_type numerical value does not map to a known $PacketType string, the packet_type value of "unknown" can be used and the raw value captured in the packet_type_bytes field; a numerical value without variable-length integer encoding.¶

PacketHeader omits the fixed bit and the reserved bits because QUIC version 1 gives them fixed values; see Section 17 of [QUIC-TRANSPORT]. Their values can be logged in the raw.data field of the event that logs the PacketHeader.¶

QUIC extensions that use these bits, such as the QUIC Bit greasing extension ([GREASEBIT]), can log that use with new events, similar to spin_bit_updated, or with fields added to PacketHeader through $$quic-packetheader-extension.¶

For long header packets of type initial, handshake, and 0RTT, the length field of the packet header is logged in the qlog raw.length field, and the value signifies the length of the packet number plus the payload.¶

8.9. Token

The token carried in an Initial packet is either a token from a Retry packet, or one that the server provided earlier in a NEW_TOKEN frame, for address validation in a later connection; see Section 8.1.3 of [QUIC-TRANSPORT]. Both kinds typically encode metadata that the server uses to check the token, but the metadata and its format are implementation-specific. The details field can log that metadata.¶

8.13. QUIC Frames

The generic $QuicFrame is defined here as a CDDL "type socket" extension point. It can be extended to support additional QUIC frame types.¶

The QUIC frame types defined in this document are as follows:¶

8.13.1. PaddingFrame

A PADDING frame is a single byte with the value 0, so each padding byte is its own frame; see Section 19.1 of [QUIC-TRANSPORT]. Logging each one as a separate PaddingFrame could add hundreds of entries to a single packet event, for example when a client pads an Initial packet to 1200 bytes. Implementations SHOULD instead log a single PaddingFrame for the packet, and set its raw.payload_length field to the number of PADDING frames in the packet.¶

8.13.2. PingFrame

8.13.3. AckFrame

The ranges in acked_ranges do not have to be in order; for example, [[5,9],[1,4]] is valid.¶

The two numbers in a range can be equal; for example, [120,120] means that packet 120 was acknowledged. In that case, implementations SHOULD log [120] instead, and tools MUST handle both forms.¶

8.13.4. ResetStreamFrame

If the error numerical value does not map to a known ApplicationError string, the error value of "unknown" can be used and the raw value captured in the error_code field; a numerical value without variable-length integer encoding.¶

8.13.5. ResetStreamAtFrame

The RESET_STREAM_AT frame is defined in Section 4 of [RESET-STREAM-AT].¶

If the error numerical value does not map to a known ApplicationError string, the error value of "unknown" can be used and the raw value captured in the error_code field; a numerical value without variable-length integer encoding.¶

8.13.6. StopSendingFrame

If the error numerical value does not map to a known ApplicationError string, the error value of "unknown" can be used and the raw value captured in the error_code field; a numerical value without variable-length integer encoding.¶

8.13.7. CryptoFrame

The length field of the CRYPTO frame MUST be logged in the qlog raw.length field. The other sub-fields of the raw field are optional.¶

8.13.8. NewTokenFrame

8.13.9. StreamFrame

If the STREAM frame contains a length field, it MUST be logged in the qlog raw.length field. If it does not, the implementation MAY calculate the actual frame byte length itself and log that in raw.length if necessary.¶

8.13.10. MaxDataFrame

8.13.11. MaxStreamDataFrame

8.13.12. MaxStreamsFrame

8.13.13. DataBlockedFrame

8.13.14. StreamDataBlockedFrame

8.13.15. StreamsBlockedFrame

8.13.16. NewConnectionIDFrame

8.13.17. RetireConnectionIDFrame

8.13.18. PathChallengeFrame

8.13.19. PathResponseFrame

8.13.20. ConnectionCloseFrame

An endpoint that receives unknown error codes can record it in the error_code field using the numerical value without variable-length integer encoding.¶

The trigger_frame_type field logs the Frame Type field, which only the transport variant of CONNECTION_CLOSE (type 0x1c) carries; see Section 19.19 of [QUIC-TRANSPORT]. A known frame type is logged as its frame type string, such as "stream". An unknown frame type is logged as the numerical value without variable-length integer encoding.¶

The reason phrase in a CONNECTION_CLOSE frame is a byte sequence, which RFC 9000 recommends be UTF-8; see Section 19.19 of [QUIC-TRANSPORT]. The reason field holds the reason phrase as text, and reason_bytes holds the raw bytes, for example when the value is not UTF-8 or when an endpoint does not want to decode it. Implementations SHOULD log at least one form and MAY log both.¶

8.13.21. HandshakeDoneFrame

8.13.22. UnknownFrame

The frame_type_bytes field is the numerical value without variable-length integer encoding.¶

8.13.23. DatagramFrame

The QUIC DATAGRAM frame is defined in Section 4 of [QUIC-DATAGRAM].¶

If the DATAGRAM frame contains a length field, it MUST be logged in the qlog raw.length field. If it does not, the implementation MAY calculate the actual datagram byte length itself and log that in raw.length if necessary.¶

8.14. TransportError

The generic $TransportError is defined here as a CDDL "type socket" extension point. It can be extended to support additional transport errors.¶

8.15. ApplicationError

Application errors are defined by the application protocol that runs on top of QUIC, such as HTTP/3, so this document cannot list them. $ApplicationError is instead defined as a CDDL "type socket" extension point, with a single "unknown" value.¶

Event schemas for application protocols MUST add their error strings by extending the $ApplicationError socket; see Section 8.2 of [QLOG-MAIN].¶

8.16. CryptoError

RFC 9001 converts a TLS alert into a QUIC error code by adding the alert's AlertDescription value to 0x0100; see Section 4.8 of [QUIC-TLS].¶

A fixed list of strings does not fit this range well, so a CryptoError value is crypto_error_ followed by the resulting QUIC error code in lowercase hexadecimal, from crypto_error_0x100 to crypto_error_0x1ff. For example, a handshake_failure alert, which is 0x0128 in QUIC, is logged as crypto_error_0x128.¶

9. Handling Packet Coalescing

Multiple QUIC packets can be coalesced into a single UDP datagram, especially during the handshake; see Section 12.2 of [QUIC-TRANSPORT]. Neither QUIC nor UDP provides a way to tell which packets shared a datagram.¶

To let tools match QUIC packet events to UDP datagram events, the optional datagram_payload_checksum field carries a 32-bit CRC32c of the UDP payload, calculated as described in Section 11.3 of [RFC9868]. The UDP datagram events carry one checksum per datagram, in their datagram_payload_checksums field.¶
